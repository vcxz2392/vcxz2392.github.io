CASE 01디라이트 파트너 · QGX · 2025.10 ~

한 프로세스에 묶여 있던 입수와 처리를 나눠,
후처리가 실패해도 원본이 남는 구조로

원본 보관실패 건만 재처리

설비가 TCP로 보낸 값을 같은 프로세스에서 바로 후처리하던 레거시를 입수 · 처리 · 웹으로 나누고, 메시지마다 어디까지 처리됐는지 남겼습니다.

문제
입수 · 처리 · 웹이 한 프로세스에 묶여 장애 격리와 독립 배포가 불가. TCP로 받은 데이터를 같은 프로세스에서 동기로 후처리해, 후처리가 실패하면 원본 기준으로 추적 · 재처리할 경로가 없어 데이터 유실로 이어지는 구조
판단
  • 도메인 경계를 지금 긋기엔 이르다고 보고 1차 분리 기준을 기술적 책임(입수 · 처리 · 웹)으로 설정. 독립 배포와 오너십이 필요해질 때마다 하나씩 떼어내는 순서
  • 재처리에는 메시지 영속과 원본 보관이 필요해 in-memory queue 대신 Kafka 채택
조치
  • 입수(Netty → Kafka Producer) · 처리(Kafka Consumer → JPA) · 웹으로 분리
  • 처리 완료 후 offset을 커밋하도록 수동 ACK 적용, 메시지 상태 기록, 원본 메시지 테이블에 원본 JSON · requestId · offset 보관
  • 실패 메시지는 단건 · 배치 · 이벤트 유형별 재처리 API로 다시 처리
결과
입수 · 처리 분리를 운영에 적용. Kafka에 적재된 메시지는 후처리가 실패해도 원본이 남아, requestId · offset 기준으로 원인을 확인하고 실패 건만 다시 처리

이 사례에서 가져가는 것

데이터를 다루는 시스템에서는 얼마나 빨리 처리하는지보다 실패했을 때 무엇이 남는지를 먼저 정합니다. 원본과 처리 상태가 남아 있으면 원인 확인과 재처리가 정해진 운영 절차가 됩니다.

CASE 02일루미나리안 · EnergySharesUS · 2021.12 ~ 2024

미국 증권 규정을
투자 상태와 검증 규칙으로

검증 규칙 12개신용카드 투자 오픈 2023 4Q

투자 한도, 취소 기한, 조건 변경 재동의 같은 규정 요구사항을 사람이 기억하는 대신, 투자와 취소 때마다 코드가 같은 규칙으로 검증하게 만들었습니다.

문제
기획 · 컴플라이언스가 정리한 미국 증권 규정(Reg CF · Reg D · Reg A) 요구사항이 투자 한도 · 취소 기한 · 조건 변경 재동의를 요구하고, 에스크로 · KYC/AML · 문서 보관은 제약이 서로 다른 외부 서비스에 의존
판단
  • 투자 상태가 에스크로 거래 상태와 1:1로 맞물리는 구조라 상태를 늘리지 않고, 재동의는 플래그로 분리
  • 웹훅 부재 · 호출 제한 · 검증 실패 같은 외부 제약은 우리 쪽 상태와 배치로 흡수
  • 마감 알림 직후 몰리는 요청은 당시 규모에서 분산 락보다 DB 트랜잭션 안의 비관적 락으로 충분하다고 판단
조치
  • 투자 검증 규칙 12개: 결제수단별 한도(카드 $5,000 · ACH $100,000), Reg CF 한도를 투자 시 차감 · 취소 시 복원, 롤링 12개월 1회 수정 제한
  • 에스크로를 FundAmerica에서 North Capital로 바꾸며 없는 웹훅은 sync로 대체, Egnyte 호출 제한은 서비스 계정 분산 배치, KYC/AML 실패 건은 결제 보류 후 수동 검토
  • 신용카드 투자 결제를 North Capital + Stripe로 연동: 수수료 부담 주체 설정, 진행 중 투자가 있으면 카드 수정 잠금
결과
규제 한도 · 결제 한도 · 취소 기한을 투자와 취소 때마다 같은 규칙으로 검증. 신용카드 투자 오픈(2023 4분기)

이 사례에서 가져가는 것

규정이 많은 도메인일수록 상태는 적게 두고, 규칙은 한곳에서 매번 같은 방식으로 검증되게 합니다. 외부 서비스의 빈틈은 그쪽이 고쳐 주길 기다리지 않고 우리 쪽 상태와 배치로 메웁니다.

운영 알람 재설계2024.09

ERROR 로그 기준

문제
알람이 Nginx 5xx 기준이라 리다이렉션으로 처리되는 에러는 감지 불가. 소셜 가입 중복 계정 에러로 약 400명이 로그인하지 못하는 동안에도 알람이 울리지 않음
조치
  • Grafana에서 최근 1분간 ERROR 로그 1건 이상을 알람 조건으로 두고 Slack 발송, 메시지에 RequestId를 넣어 요청 단위로 추적
  • 슬로우 쿼리 1초 기준 알람을 개발팀 전용 채널로 분리
결과
5xx에 안 잡히던 에러와 슬로우 쿼리까지 알람 대상으로 확대. 누적 가입 오류는 RequestId로 추적해 동시성 문제로 확정하고 유니크 키 제약으로 차단. 같은 방식을 사내 다른 프로젝트에도 적용

이 사례에서 가져가는 것

사용자 요청 경로에는 그 순간 꼭 필요한 일만 남기고, 나머지는 다시 시도할 수 있는 곳으로 보냅니다. 알람은 서버 응답 코드가 아니라 사용자가 실제로 겪는 실패를 기준으로 겁니다.

CASE 04디라이트 파트너 · QGX · 2025.03 ~

AI 리포트 조회를
SQL 생성에서 API Tool 호출로

2분 → 10초리포트 1건 생성

AI가 매번 SQL을 만들어 DB를 직접 읽게 두는 대신, 도메인 규칙이 이미 들어 있는 백엔드 API를 Tool로 부르게 바꿨습니다.

역할 경계  AI 파이프라인 본체(워크플로우 · 프롬프트)는 AI 담당 동료 몫. 본인은 느린 원인 분석, 조회 방식 전환, Agent가 호출할 API Tool 제공

문제
리포트 1건 생성에 약 2분. Agent가 SQL을 생성해 DB를 직접 조회하는 구간이 느리고, 생성된 쿼리가 의도와 다른 데이터를 가져와 원하지 않는 답변이 나오는 상태
판단
매번 쿼리를 생성하게 두는 대신 도메인 규칙이 이미 들어 있는 백엔드 API를 Tool로 호출하게 하면, 느린 조회 구간과 의도와 다른 쿼리가 생기는 경로를 함께 없앨 수 있다고 판단
조치
  • LangGraph 흐름에서 조회가 일어나는 지점을 파악해 필요한 조회를 사전 정의된 REST API Tool로 제공
  • AI 담당 동료와 Tool 명세, 요청 · 응답 계약 협의
결과
리포트 1건 생성 2분 → 10초. 해당 리포트 흐름의 SQL 생성 · 직접 조회 구간을 Tool 호출로 대체했고, 이후 리포트도 같은 Tool 계약을 재사용

이 사례에서 가져가는 것

AI 기능이 느리거나 엉뚱한 답을 낼 때, 모델이나 프롬프트보다 먼저 데이터를 어디서 어떻게 가져오는지를 봅니다. 이미 검증된 백엔드 API를 Tool로 열어 주는 것이 백엔드 개발자가 AI 기능에 가장 직접 기여할 수 있는 지점이라고 생각합니다.
