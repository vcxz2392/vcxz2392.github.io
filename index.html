Case 01 · QGX · 2025.10 ~

한 프로세스에 묶여 있던 입수와 처리를 나눴습니다

TCP로 받은 설비 데이터를 같은 프로세스에서 동기로 후처리하던 구조라, 후처리가 실패하면 데이터가 그대로 사라졌습니다.

01 / 분리 기준

도메인 대신 기술적 책임으로 먼저 자름

도메인 경계를 지금 긋기엔 이르다고 보고 1차 기준을 입수 · 처리 · 웹으로 정했습니다. 독립 배포와 오너십이 필요해질 때마다 하나씩 떼어내는 순서입니다.

  • 입수: Netty → Kafka Producer
  • 처리: Kafka Consumer → JPA
  • 웹: 조회·집계 API

02 / 상태 기록

메시지마다 어디까지 갔는지 남김

재처리에는 메시지 영속이 필요해 in-memory queue 대신 Kafka를 골랐습니다. 수동 ACK로 처리 완료 시점을 직접 정하고, 메시지 상태를 기록합니다.

  • CONSUMING → PROCESSING → SUCCESS / FAILED
  • traceId · requestId를 Kafka 헤더와 MDC로 넘겨 입수 로그와 처리 로그를 같은 ID로 연결

03 / 원본 보관과 재처리

실패한 건 원본으로 다시 돌림

원본 JSON, requestId, topic · partition · offset을 원본 메시지 테이블에 보관합니다. 실패 메시지는 단건 · 배치 · 이벤트 유형별 재처리 API로 다시 처리합니다.

  • 운영에 적용해 결합 해소
  • 장애 시 원본 메시지와 requestId로 원인 확인과 재처리 가능
SUCCESS 0FAILED 0재처리 0

흐름도의 메시지와 숫자는 동작을 보여주는 시뮬레이션입니다.
